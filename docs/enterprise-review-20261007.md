# CampusEats 企业工程审查与个人开发改造计划

审查日期：2026-10-07。源码基线：`3dcc113`，审查开始时 Git 工作区无已跟踪文件改动。范围：Java 后端、SQL、Maven 实际打包依赖、Compose/Nginx、已有前端补丁和自动化检查。

## 1. 结论与合理目标

当前项目是业务功能较完整、已有可靠性修复和部署验证的单店本机演示系统。基础点餐流程具备，但还没有达到可承接真实用户与资金交易的小规模生产系统要求。

评价企业项目，应看交易是否正确、失败是否可恢复、权限是否受控、问题是否可定位、发布和恢复是否可重复。微服务、Kafka、Kubernetes、多租户和复杂领域模型都不是本项目的必选项。

建议个人开发目标为：**单校区、单店、单体部署；独立用户身份、正确的订单与退款状态、简单员工权限、可验证的容量边界、可恢复的数据，以及可维护的前端。** 以下计划按这个范围制定。如果未来明确做多店平台，再增加商户隔离、入驻、结算和跨店购物车。

本报告中的“源码确认”表示实现已核对；“服务层复现”使用真实服务类与 Mock 数据依赖；“风险推断”表示按调用顺序推导的失败场景；“建议目标”不是当前性能或行业统一标准。

## 3. 代码结构评价

### 3.1 已有结构值得保留

- Maven 三模块、Controller → Service → Mapper、DTO/Entity/VO 分离，适合目前体量。
- 管理端与用户端接口分开；订单提交、菜品口味和套餐关联等多表写入已有事务。
- 用户归属校验、请求结束清理 ThreadLocal、员工禁用状态检查已经实现。
- 订单主要操作已有 `WHERE id=? AND status=?` 条件更新；模拟支付还有用户和支付状态条件。
- 服务端计算订单金额并校验当前售价/起售状态，不直接信任客户端总金额。
- 有本地 Compose、随机基础设施/JWT 密钥生成、非 root Java 容器、持久卷、健康检查、启动和回归脚本。

### 3.2 当前边界不清的地方

| 位置 | 源码事实 | 个人开发可做的调整 |
| --- | --- | --- |
| 三模块依赖 | `sky-server` 同时依赖 `sky-common` 与 `sky-pojo`；`sky-pojo` 并未直接依赖 common | 修正文档中的串行依赖图 |
| `sky-pojo/pom.xml` | 数据对象模块引入 knife4j starter，并显式声明旧 Jackson 版本 | 文档与 Web starter 留在 server；数据对象只依赖必要注解/基础库；版本由 BOM 管理 |
| `OrderServiceImpl` | 下单、计价、支付、取消、列表组装、百度地图调用、通知集中在同一类 | 渐进拆为订单写入、订单查询、计价、支付和配送校验服务；保留同一应用与数据库 |
| 缓存 | 菜品手写 Redis、套餐用 Spring Cache，失效操作在 Controller | 统一缓存策略，业务修改提交后失效；后台任务调用服务也应触发失效 |
| `sky-common` | 同时包含通用结果/异常和微信支付、OSS、HTTP 集成 | 把外部集成放到 server 的独立 integration 包；公共模块保持轻量 |

| 全局响应 | 常见业务错误是 HTTP 200 + 业务失败码；未形成稳定错误分类与请求标识 | 定义参数错误、认证、权限、状态冲突、限流、依赖失败的契约，前后端同步适配 |

本次 JAR 的 Jackson 实际为 `2.13.3`；不能将 pojo POM 中的 `2.9.2` 直接当作 server 最终运行版本。`allow-circular-references=true` 是配置事实，本次没有确认真实循环依赖。

无需一次性重写所有包或实现完整 DDD。优先让权限、状态和缓存规则集中在业务服务中，避免不同入口执行不同规则。

## 4. 优先处理的问题

优先级含义：**P0：开放真实用户/公网/资金交易前的门槛；P1：小规模试用前应补齐；P2：有明确需求或容量证据后再扩展。** 这些优先级不是对当前本机环境被攻击的断言。

| 编号 | 优先级 | 问题和证据 | 最小处理方式与验收 |
| --- | --- | --- | --- |
| R01 | P0 | `/ws/{sid}` 无身份检查，连接由客户端 sid 标识并向所有会话广播订单号；HTTP JWT 拦截器只覆盖 admin/user | 握手认证、员工权限与 Origin 白名单；服务端会话标识；无凭据连接拒绝，过期/退出连接关闭 |
| R02 | P0 | 员工密码为 MD5，新增员工使用统一默认密码；所有启用员工共享同一组后台权限 | 升级密码哈希、初始化/强制改密流程、最小角色权限、登录限流；普通员工不能管理员工或改营业配置 |
| R03 | P0 | logout 仅返回成功；改密没有令牌撤销；用户令牌仅验签与提取 ID | 增加 tokenVersion/authVersion 或 jti 撤销；退出及改密后旧令牌拒绝；真实用户支持禁用 |
| R04 | P0 | Compose 默认共享演示用户和模拟支付；关闭模拟支付只拒绝付款，不会开启真实支付 | 单独 prod 配置，启动时拒绝演示身份/模拟资金/弱密钥；保留 test/demo profile，明确业务模式 |
| R05 | P0，支付启用前 | 回调只解密，未核对签名头、商户/应用、金额与交易状态；`paySuccess` 无状态条件 | 未交付真实支付前禁用遗留回调；正式接入时使用官方验签机制、支付流水唯一约束、幂等和合法状态迁移 |
| R06 | P0 | 最终 JAR 包含 Fastjson 1.2.76，Spring Boot 2.7.3 等老依赖 | 删除不必要的 Fastjson/旧版本覆盖；扫描最终依赖和镜像，升级到执行时仍受支持的框架版本 |
| R07 | P1 | 下单没有设置 `orders.address`；后台列表读取当前地址簿。服务层确认传给 insert 的地址为空 | 下单保存完整地址快照；所有订单页面读快照；修改/删除地址后历史和配送订单地址保持不变 |
| R08 | P1 | 下单无服务端幂等键；先读购物车，再插入订单，最后按 userId 清空 | 订单请求键 + 数据库唯一约束；同键重试返回原结果；购物车版本与写入互斥；重复请求不能生成重复订单或清掉新加商品 |
| R09 | P1 | 购物车先查后写绝对数量，无商品组合唯一约束；减项没有和加项一致的商品校验 | 规范化商品/口味键 + 唯一约束，数量原子增减；空减项 DTO 拒绝；实库并发计数正确 |
| R10 | P1 | 编辑菜品可提交 status 并直接写入，绕过联动停售；编辑套餐也可绕过专门起售检查；菜品联动停售未包事务 | 状态修改只走统一业务方法；跨菜品/套餐更新包事务；停售菜品不能通过编辑入口继续在起售套餐中售卖 |
| R11 | P1 | 套餐仅校验非空关系列表；关联实体存在性、份数、分类类型和价格来源未统一校验；普通地址编辑可写 isDefault | Bean Validation + 引用校验 + 服务端补全；禁用越权字段绑定；默认地址通过一个原子入口修改 |
| R12 | P1 | 每日任务按下单时间判断派送超时并直接完成；没有用户确认或异常派送记录 | 保存派送开始时间；超时先转异常/待核验或按明确规则自动收货；不能把刚开始派送的旧订单自动当已送达 |
| R13 | P1 | 微信/百度 GET 未设置已有的超时配置；登录方法 synchronized 将所有登录串行化 | 统一有连接/读取/整体预算的 HTTP 客户端；唯一 openid 约束替代全方法锁；慢依赖不阻塞所有用户 |
| R14 | P1 | 通知直接在支付请求里同步广播；重启、失败、断线没有持久补偿 | 订单表作最终事实；重连查询待处理订单；关键通知可用数据库事件表 + 定时重试，不需消息队列 |
| R15 | P1 | SQL 初始化只处理新卷；没有版本迁移、CI、实库集成测试、备份恢复记录；健康检查只查 Redis 营业状态 | 增量数据库迁移、CI、MySQL/Redis 集成测试、readiness 检查与定期恢复演练 |

### 4.1 五个已进行的服务层复现

1. **地址快照缺失**：给真实 `submitOrder` 合法地址和购物车，捕获 `OrderMapper.insert` 参数，其 `address` 为 null。
2. **遗留回调打开已取消订单**：为 `paySuccess` 返回已取消/退款订单，捕获其调用普通 `update` 将状态设为待接单、支付状态设为已支付。Mapper XML 的条件只有主键，没有旧状态限制。
3. **空减项请求误操作**：给 `subShoppingCart(new ShoppingCartDTO())` 返回当前用户购物车，其第一条数量从 2 被改为 1。真实 XML 在没有商品条件时只按用户查询，入口未拒绝这个请求。
4. **编辑入口绕过停售联动**：调用 `updateWithFlavor(status=0)`，确认执行菜品状态修改而没有访问套餐或关联 Mapper。
5. **购物车并发丢更新**：两条线程都读取数量 1 后再继续，实际服务逻辑两次都调用写数量 2，无法累加为 3。实际数据库结果还需集成测试确认。

回调风险需要区分暴露面：当前 Nginx 没有 `/notify/` 反向代理配置，Java 服务未发布主机端口，默认入口也只绑定本机。不能说当前任何公网访客已能伪造回调；AES 解密也不是无需密钥的任意 JSON 写订单接口。但是一旦接通真实回调，合法通知的重复、乱序或迟到就会遇到上述状态问题。

## 5. 缺少哪些业务功能：按必要程度补

| 能力 | 当前程度 | 个人开发最小版本 | 必要程度 |
| --- | --- | --- | --- |
| 独立用户身份 | 演示模式共用一个身份；有微信 code 换取身份的代码，未验收 | 验证真实登录；数据库唯一 openid；校区/楼栋可选；演示模式独立隔离 | 真实多用户必需 |
| 下单确认与幂等 | 服务端计价已有；超时重试和并发快照未闭合 | 提交确认页显示最终金额；一次操作稳定请求键；重试返回原订单 | 必需 |
| 售卖数量限制 | 起售/停售有，库存与供餐上限没有 | 每日可售份数；数据库条件扣减、取消释放；套餐按实际组成校验 | 真正承接有限供餐时必需 |
| 配送规则 | 单店地址与百度路线代码；本机默认跳过；距离阈值硬编码为 100000 米 | 校区/楼栋白名单、可配置配送费与营业时段、配送联系人/备注 | 校园实际试用必需 |
| 订单履约轨迹 | 接单、派送、完成与取消有；操作日志和可靠送达规则不足 | 状态时间线、操作人/原因、派送开始时间、异常订单人工处理 | 必需 |
| 支付/退款闭环 | 目前仅本地状态模拟 | PaymentGateway 接口 + Mock 实现；支付/退款记录、处理中/成功/失败状态、重试及查询补偿 | 工程展示可先模拟；真实收费前必须真实验收 |
| 员工权限/审计 | 只有启用状态，没有职责隔离和独立审计流水 | 管理员、接单员工、配送员工三个角色；敏感操作留审计 | 必需 |
| 售后入口 | 有取消/拒单；没有完整售后处理 | 取消原因、退款进度、问题反馈与人工处理页 | 小范围试用建议 |
| 搜索与个人资料 | 当前以分类浏览和微信登录为主 | 简单关键词搜索、联系人维护 | 有用户需求再做 |
| 优惠券/积分/评价 | 未发现对应业务模型 | 先做普通评价或一种优惠规则，定义计算顺序和上限 | 可延后 |
| 多店/多校区/骑手抢单 | 没有平台隔离与结算模型 | 当前单店阶段不列入门槛 | 明确转平台后再做 |

库存不必从 Redis 秒杀方案开始。可用 MySQL `UPDATE ... SET available=available-? WHERE available>=?` 检查影响行数，并在同一事务记录订单与预占；超时取消/退款是否释放、以及只释放一次，需要状态和预占记录共同约束。套餐数量先按组成菜品计算，避免只扣套餐而漏扣有限餐品。

下单幂等的关键不只是不让第二次执行。推荐 `(user_id, request_id)` 唯一，保存请求指纹和结果订单；同键不同内容报冲突，同键成功重试返回原结果。成功写订单、扣减/预占、记录幂等结果、清理对应购物车应形成原子边界。可锁用户购物车根记录并校验版本；加减项也需遵守同一规则。前端超时后保留原键并查询结果，不能每次重试生成新键。

模拟支付也可以体现完整工程能力：支付与订单状态分开，模拟重复/迟到回调、支付成功但本地超时、退款失败重试和人工核对；始终标注模拟。获得实际接入条件后才完成官方通道，不能以本地改状态作为资金到账/退款证据。

## 6. 性能怎么改：先减少确定的浪费

目前不能给出 QPS、最大同时在线人数或 p95 延迟。源码缺少索引和批量查询是确定事实，但其具体影响取决于数据量、冷热缓存、机器资源和请求分布。

### 6.1 SQL 与查询次数

| 热点 | 源码计算/观察 | 改进 |
| --- | --- | --- |
| 用户订单分页 | 返回 N 单后逐单查明细：数据查询 `1+N`，一般另有一次分页 count | 一次查订单页、一次按 orderId 集合查明细；加 count 后一般 3 次，查询次数不随页内订单数增加 |
| 管理订单列表 | N 单逐单查明细和地址：数据查询 `1+2N`，一般另有 count | 使用订单地址快照，并按页批量查明细；一般 3 次查询含 count |
| 菜品菜单缓存未命中 | 查菜品后每个菜品单查口味：`1+N` | 批量查口味并分组，合计 2 次数据查询 |
| 用户统计/订单统计 | 按每日执行多次 SQL，跨度已有最多 366 天限制 | 日期范围内做条件聚合与分组，应用层补齐无数据日期 |
| 30 日 Excel 导出 | 1 次区间概览 + 30 次每日概览，每次调用 4 个 Mapper 查询，共 124 次 | 订单按日一次聚合、用户按日一次聚合，再组装概览；可将取数压缩到约 2 次聚合查询 |
| 下单 | 每个购物车商品分别查菜品/套餐 | 按 ID 批量查询价格与状态；库存锁按统一顺序获取 |
| 登录 | 全方法 synchronized，外部网络也在锁内 | 数据库唯一约束和注册竞争处理；外部请求不持有全局应用锁 |

这些是源码调用次数，不是抓取到的实际 SQL 延迟或优化后实测收益。不要用“124 次 → 2 次”推导固定百分比延迟改善。

### 6.2 优先考虑的索引与约束

初始化 SQL 中 orders、order_detail、shopping_cart、address_book、user、dish_flavor、setmeal_dish 只有主键，缺少对应业务访问索引。尚未读取停止容器中的现有库结构，所以这里针对仓库初始化定义，不断言历史数据库一定没有手工索引。

| 表 | 建议候选 | 目的 |
| --- | --- | --- |
| orders | 唯一 number；`(user_id, order_time, id)` | 支付精确查询、用户历史页、稳定时间排序 |
| orders | `(status, order_time, id)` | 待处理订单、超时任务；条件很多时以执行计划决定 |
| order_detail | `(order_id)` | 批量查询明细与订单关联 |
| shopping_cart | `(user_id)`；规范化商品/口味组合唯一键 | 购物车读取与避免重复行 |
| address_book | `(user_id, is_default)` | 用户地址与默认地址查询；索引本身不保证默认地址唯一 |
| user | 唯一 openid；需要用户日报时考虑 `(create_time)` | 身份唯一与统计 |
| dish / setmeal | `(category_id, status)` | 分类菜单 |
| dish_flavor | `(dish_id)` | 口味查询 |
| setmeal_dish | `(setmeal_id, dish_id)`；按反查需求考虑 dish_id 前导索引 | 套餐组成与停售联动 |

`(user_id, order_time, id)` 并不能同时完美覆盖“按用户+状态筛选”的所有情况；是否另加 `(user_id, status, order_time, id)` 应由主要请求分布、EXPLAIN 和写入成本决定。也不要默认把所有候选索引全建一遍。

购物车唯一键不能直接依赖可空的 dish_id/setmeal_id/flavor 组合：MySQL 唯一索引允许 NULL 带来多行情况。更容易维护的结构是非空 `item_type + item_id + normalized_flavor_key` 与 userId 组合唯一。加唯一约束前先处理历史重复数据。

订单号/手机号的 `%关键词%` 查询不能指望普通 B-tree 解决全部扫描。订单号和完整手机号优先精确匹配，需要前缀搜索再明确支持；小体量菜名模糊查询先接受其成本。用稳定的 `order_time,id` 排序，在确认深分页变慢后增加游标分页。

索引选择与左前缀原则参考 [MySQL 官方索引说明](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html)。优化前后必须保留相同数据集与实际执行计划。

### 6.3 Redis、外部调用与内存

- 菜品缓存写入没有 TTL，空列表虽写入却在读取时仍判未命中。给菜单设置短 TTL 与随机偏移；空结果短期缓存；先校验分类参数。TTL 长度按能接受的菜单陈旧时间确定。
- 正常业务失效用受影响分类的精确 DEL，分类变化时处理旧、新分类；批量维护需要遍历时才使用 SCAN。当前 `RedisTemplate.keys` 调用 KEYS，其复杂度随整个数据库键数增加。[Redis 官方 KEYS 文档](https://redis.io/docs/latest/commands/keys/)
- 数据提交后清缓存，缓存失败记录告警并由 TTL 限制陈旧期；需要更强恢复再加事件重试。仅“删缓存”仍有并发旧值回填窗口，下单继续以数据库售价/库存为准。
- 非关键菜单缓存异常可以受限回源，不宜无条件让全部流量打到数据库。店铺营业状态目前只存 Redis，它是业务配置，建议 MySQL 存最终值、Redis 做加速；取不到最终状态时停止下单并给明确提示。
- Redis 容器有 128m 内存上限，但未看到 Redis maxmemory/淘汰策略配置。设置留有进程开销余量的内存预算；业务状态与幂等记录不能按纯菜单缓存随意淘汰。
- HTTP GET 没用 `builderRequestConfig`；POST 有分项 5 秒超时，但每次创建客户端且没有完整资源管理。统一连接池、连接/读取/总体预算、错误映射，用 try-with-resources；取消/付款不能盲目重试有副作用的外部调用。
- 百度配送在下单事务内触发外部 HTTP。先完成远程校验，再进入短写事务并重新校验购物车版本、价格/库存；单校区先用楼栋配送白名单可降低外部依赖成本。
- WebSocket 当前逐会话同步发送，慢连接可能拖长支付/催单请求。使用有界异步发送、超时和失效连接清理；用户重连仍能查询待处理订单。
- 明确数据库连接池最大值、等待超时与 Redis 超时；按监控调整 Tomcat 线程和 JVM 堆，不先把所有上限调大。现有资源配额与 Java 堆比例是保护措施，尚无负载数据证明它们最优。

### 6.4 个人可执行的容量验收

1. 独立测试库准备一个固定数据集，例如 1 万订单、5 万明细及独立测试用户；记录机器、Docker 资源、JDK、数据集和提交 SHA。
2. 分别测热缓存/冷缓存菜单、用户与管理订单页、提交订单、导出，使用 20/50/100 虚拟用户逐级加压并明确思考时间和请求比例。
3. 不使用共享 demo 身份代表多用户。写入场景必须每个用户有独立购物车，并验证幂等键和数据清理。
4. 记录 p50/p95/p99、吞吐、业务正确性、错误率、CPU/内存、数据库连接等待、慢 SQL 和缓存命中率。
5. 可先把热菜单 p95 < 300ms、普通订单查询 < 500ms、无外部支付/地图的下单 < 800ms 作为 50 VU 场景的首轮建议门槛。数字是待测目标，应按资源与体验修订，不能写成当前结果。
6. 做少量故障验证：Redis 不可用、微信/地图慢响应、通知断线、提交结果回传超时、服务重启。重点是不重复订单、不超卖、状态不倒退、恢复后能查回结果。

负载发生器和被测应用共用本机时，报告要注明资源竞争。实际成功下单吞吐与纯读取吞吐分开记录。先完成一轮基线，再针对瓶颈优化和复测，不能先承诺支持多少学生同时点餐。

## 7. 安全防护的最低可维护方案

| 领域 | 最小措施 | 本项目注意点 |
| --- | --- | --- |
| 密码 | 优先 Argon2id；既有系统也可选择成熟 BCrypt 方案；登录成功后迁移旧 MD5，管理员先更换默认凭据 | 密码字段扩为适合编码哈希的长度；使用 PasswordEncoder，不自行实现算法；不要改成普通 SHA-256 |
| 角色权限 | 管理员/接单/配送三类；统一服务端授权，默认拒绝；必要接口检查订单归属 | 当前启用员工可访问员工管理、商品、报表、营业设置等全部后台入口 |
| 会话 | jti 或 authVersion、过期、改密/退出撤销；用户禁用 | 现有 JWT 已验签与过期，不等于已有会话撤销；不需要自行重写 JWT 库 |
| WebSocket | WSS、握手认证、Origin 白名单、连接数/消息长度限制、会话过期断开 | 浏览器不能任意设置握手自定义头；可使用短期一次性 ticket，避免把长期 JWT 放入 URL/日志；Origin 不是身份认证 |
| 输入 | DTO + Bean Validation，长度、数量、金额、日期范围、状态枚举、商品归属和引用存在性检查 | 当前已有部分手工校验和分页上限；补全而不是宣称现有接口完全没有校验 |
| 上传 | 限制大小和像素尺寸，检查文件签名并实际解码，接受可处理的格式，必要时重编码；配额、nosniff | 已有 10MB、扩展名白名单、UUID 文件名和固定目录；还缺真实图片内容验证，不能只补扩展名 |
| 限流 | 登录按 IP + 账号、下单按用户、催单按用户/订单、导出按员工；正确返回 429 | Nginx 简单入口限流加服务端业务限流；只信任自己代理维护的来源地址 |
| 网络 | HTTPS/WSS；只暴露代理；数据库/Redis 内网；后台文档在 prod 关闭或受控 | 当前默认本机绑定、DB/Redis 不发布端口是已有保护；公网部署再补 TLS 与防火墙 |
| 日志/隐私 | 请求 ID、订单 ID、操作人、结果；隐藏密码、JWT、完整手机号/地址和支付解密全文 | 回调仍打印请求体与解密全文；员工 DTO 含手机号/身份证号。校园点餐无实际用途的身份证字段可删去或停止采集 |
| 密钥 | 环境/秘密文件注入、仓库忽略、镜像不打入开发凭据、定期轮换 | 随机基础设施/JWT 密钥和 dev 配置排除已实现；仍需 prod 启动检查和密钥备份权限控制 |
| 供应链 | Maven 依赖与镜像扫描、按框架 BOM 管理版本、版本更新验证 | 已确认最终 JAR 版本；没有完成扫描，不能列出未经验证的完整漏洞清单 |

密码方案参考 [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)，WebSocket 防护参考 [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)。具体哈希参数需要按机器测试，安全性与登录限流、资源预算一起验收。

Spring 官方已宣布 Boot 2.x 的开源支持结束；这个项目不能将 2.7.3 当作长期安全维护基线。迁移涉及 javax → jakarta、MyBatis starter、接口文档和 JWT/Redis 兼容，需要专门一阶段处理。[Spring 官方公告](https://spring.io/blog/2023/11/23/spring-boot-2-7-18-available-now/)

Fastjson 官方公告说明 ≤1.2.80 在特定依赖条件下存在风险，当前最终 JAR 是 1.2.76。这证明需要优先处理依赖，但本次没有验证可利用链。当前优先用框架已集成的 Jackson 或经过核验的维护中库替换，不能把历史公告中的升级版本当作永久无漏洞承诺。[Fastjson 官方安全公告](https://github.com/alibaba/fastjson/wiki/security_update_20220523)

真实支付回调应先使用官方签名校验与解密机制，再验证业务字段、流水唯一性、订单状态和金额。异常或超时通过查询与对账恢复，不能直接把退款标为成功。[微信支付官方 SDK 回调说明](https://github.com/wechatpay-apiv3/wechatpay-apache-httpclient#回调通知的验签与解密)

MyBatis 已查看的 Mapper 使用 `#{}` 参数绑定，没有发现 XML 中 `${}` 拼接。不能仅因使用 MyBatis 就判定存在 SQL 注入。前端 XSS、跨域/CSRF 则需按真实源工程和最终认证方式验证，当前未得到完整结论。

## 8. 交付、观测和恢复

- **数据库升级**：选 Flyway 或另一种简单版本迁移方式。初始化 SQL 仅适用于新数据卷；为已有数据库新增索引/约束应提供检查重复数据、执行迁移、失败恢复的步骤，不能删除卷重建。
- **最低 CI**：后端验证、两端逻辑检查、最终依赖扫描和镜像构建检查。补真实 MySQL/Redis 集成测试，覆盖并发增减、唯一键、状态条件更新和事务回滚。
- **健康检查**：liveness 判断进程是否活着；readiness 检查关键依赖是否能服务。当前 `/user/shop/status` 只访问 Redis，即使 MySQL 不可用也可能返回成功。Actuator 是可选的现成实现，管理端点应限制暴露范围。
- **观测**：结构化日志 + requestId；接口耗时/错误、连接池等待、慢 SQL、退款/后台任务失败、通知积压与最后成功时间。个人阶段先有可查日志和关键指标，有需要再用 Prometheus/Grafana。
- **备份恢复**：MySQL 数据、上传图片、配置和迁移版本一起备份；保护备份内个人资料/密钥，定期在独立空库恢复并核对。Docker 持久卷只能抗容器重建，不能替代备份。
- **发布恢复**：保留上一个可用镜像；迁移优先采用兼容性扩展步骤，使旧应用可回退。不要把数据回滚、应用回滚、重启混为同一操作。
