# CampusEats v1 架构与接口

## 模块与业务边界

- sky-common：业务异常、摘要工具，不依赖 Web 框架。
- sky-pojo：请求、分页、购物车及报价契约与校验。
- sky-server：认证、交易、查询、商品、校园规则、异步任务、通知和上传。

Controller 负责协议与参数校验；业务服务负责权限、状态和事务。订单与目录的批量读取使用 MyBatis；条件写入及事务内行锁通过 JDBC 明确执行。两者共享 Hikari 数据源和 Spring 事务。这是同一数据库内的职责分工。

## 交易

用户购物车根记录串行化同一用户操作。MySQL使用READ COMMITTED；商品与规则校验在锁保护下读取。每日配额按营业日期和菜品有条件扣减，套餐先合并组成份数并按菜品ID顺序锁定。普通扣减直接UPDATE；仅初始化/份数不足分支使用独占锁upsert再校验，初始化不覆盖已有总配额。配额操作位于事务末尾，避免热门行锁持有期间执行其他订单SQL。

订单、快照、预占流水、购物车清理、审计、Outbox 同事务提交。用户和请求UUID建立唯一约束，请求摘要不允许同键换内容。重复请求返回同一订单当前状态。

所有订单操作带版本；状态竞争只允许一个结果。支付是明确模拟网关；取消不直接把支付状态改为退款。持久化退款任务有租约、有限重试和人工重试。接单后的消耗流水保留，不因退款自动恢复。

Outbox任务持久化并允许重领，发送尝试可能重复。WebSocket是尽力通知：任务成功表示本机发送队列已接收，不表示客户端已收到；发送失败或进程退出时通知可能丢失。通知事件有eventId，客户端去重并重查订单，页面每15秒刷新。数据库订单状态是事实来源。执行任务租约30秒，中断后可重新领取；模拟退款使用稳定订单引用，无重复资金效果。领取任务使用现有状态索引及SKIP LOCKED，避免优化器为了ORDER BY id/LIMIT选择扫描大量成功历史记录的主键路径。

## 权限与会话

JWT 使用 HS256 并校验 issuer、过期时间、jti 和数据库会话。每次请求检查账户状态及授权版本。管理员管理全站，运营员处理订单，配送员限自己的派送订单。改密、角色或启用状态变化撤销旧会话。

密码 Argon2id：19 MiB/2次/并行度1。旧 MD5 验证成功后迁移，初始密码必须修改。登录限流按账户、IP；订单写入按用户限流。Redis不可用时使用本机有界窗口，最多10000个键；容量准入与计数串行保护，满表先按各键自己的到期时间回收，Redis恢复后优先使用Redis。

WebSocket 仅运营员工使用，需30秒一次性Redis票据及允许的Origin；每员工最多2连接，全局100连接，发送队列有上限。Redis中断时不能新建实时连接，页面继续轮询。

## 协议

- /api/v1/admin：管理员、运营员、配送员；/api/v1/user：点餐用户。
- 统一响应 code/message/data/requestId。HTTP状态反映参数、认证、授权、冲突、限流和依赖故障。
- 业务金额使用十进制字符串，日期使用北京时间偏移ISO格式，订单等长整型ID使用字符串。
- POST /user/orders 必须携带 Idempotency-Key；先 checkout/preview，再携带 cartVersion、quoteHash 提交。
- 请求失败仍不确定是否提交成功时，保留请求键并调用 orders/by-request/{key}；404再用同一原请求重试。
- 商品、地址、购物车、订单所有权由服务端限制，客户端路由限制只是交互提示。

## 查询与缓存

订单分页为计数、订单页、批量明细，查询次数不随页内订单数增长。历史地址从订单快照读取。菜单批量加载口味或套餐组成；配额实时查询，静态目录缓存240至360秒，空列表30秒。

目录变更在业务事务中写入缓存失效Outbox，提交后立即尝试按分类精确失效；菜品及其分类变化也失效依赖菜品的套餐分类，相同键去重。持久任务负责补偿失败或提交后进程中断。单实例内使用256个固定分片的公平读写锁，回源与回填持读锁，提交后删除、直接删除和Outbox重试统一持写锁，避免旧查询在失效完成后重新留下旧缓存。回源并发限制20，最终下单以数据库校验为准。统计按天聚合，导出复用结果。

删除分类前先锁定分类行，再检查商品引用并写入删除审计；商品创建持同一分类的共享锁。等待并发创建提交后，删除方重新检查引用，不留下无分类商品。

## 边界

单店单实例，不包含商户结算或真实支付能力。运营时间当前每天采用相同的多个时段。自动配送超时只作标记。个人工程展示的容量数据需绑定实际机器、镜像和数据集。
