# 多校区版本部署与恢复

首次部署见[项目首页](../README.md)，前端开发和微信小程序配置见[开发指南](development.md)。本文用于已有数据环境。

## 已采用 CI 制品的日常环境

CI 在同一镜像上完成浏览器回归、独立恢复和安全扫描，成功的 master push 生成 `release-<完整提交SHA>` 制品。下载时指定成功 run、来源 SHA 和 CI 日志中的 `RELEASE_MANIFEST_SHA256`，不选择名称相似的包、不沿用失败 attempt。

```powershell
pwsh -NoProfile -File ./scripts/download-release.ps1 -RunId <成功run> -SourceSha <完整SHA> -ManifestSha256 <清单摘要> -Destination .local/releases/download-<SHA>
pwsh -NoProfile -File ./scripts/release.ps1 -BundleDirectory .local/releases/download-<SHA> -ExpectedSourceSha <完整SHA> -ExpectedRunId <成功run> -ExpectedManifestSha256 <清单摘要>
```

下载使用当前 GitHub 凭据或进程内 `CAMPUS_GITHUB_TOKEN` 的 Actions 读取权限，不把令牌写入参数、文件或日志。制品校验包括归档与扫描报告哈希、镜像 ID／架构／revision、成功 run 及 attempt；迁移内容使用明确的 `utf8-lf-v1` 规范化摘要，避免 Windows 与 Linux 的换行差异。未知格式、来源不匹配或过期制品均停止发布。

大文件使用4 MiB分段传输，每段最多3次尝试；只恢复本次调用已经确认的前缀，不接续已有文件。单次请求90秒取消覆盖响应体，整体传输预算15分钟；每段的范围、总长度和实际字节数均须匹配，最终仍校验GitHub提供的完整归档SHA-256。GitHub认证只发送到官方API，存储地址不携带该认证，下载失败不进入发布。

发布清单分别记录源引擎运行ID、配置摘要和平台清单摘要。读取可信OCI归档时逐项验证索引、清单、配置及有序层的内容地址；导入后本机ID必须属于该图中已验证的配置／平台清单身份，文件系统层顺序、平台和源码revision也必须匹配。Compose固定本机已解析的内容ID，容器再次核对实际引用。仅有同名标签、相同revision或相同架构不能通过验证。

发布保持 Web 停止，先备份并在独立恢复容器验证，再仅启动关闭后台任务的候选 Java 执行 Flyway。原表原列、原主键记录及上传卷挂载核对后，生成新 schema 的当前恢复集并独立恢复，比较原上传路径、大小及哈希。全部通过后才恢复正常后台任务并开放 Web。MySQL、Redis 容器和三个日常数据卷保持不变。

发布失败保持停写并保存现场，不自动切旧应用搭配新 schema。成功后将应用引用固定为 CI 标签、依赖固定为原镜像 ID；后续普通 Compose 启动继续使用该版本。`start.ps1` 拒绝在这种环境中源码覆盖构建。

独立角色验收采用全新 `campuseats-improvement-...` 项目和非日常端口，使用同一制品及匹配依赖镜像。只在明确全新环境为发布入口增加 `-Initialize -ProjectName <独立项目> -EnvFile <独立配置>`；它拒绝复用已有同名容器或卷。验收数据不能复制回日常库。

当前恢复材料必须同时保留已验证数据库／上传／配置、CI 应用制品和四服务镜像归档，记录摘要及来源；不能仅依赖浮动镜像标签或 GitHub 的短期 artifact 保留期。只保留最新版的策略在新版本与当前恢复材料均验证后执行，过程中的临时留底不提前删除。

## 首次本机部署与尚未采用制品的源码环境

1. 完成后端、前端、接口契约和独立容器验收；日常数据不用于写入式测试。
2. 保留当前运行容器对应的应用和 Web 镜像。运行 `scripts/start.ps1` 会先构建，构建失败不会停止旧应用。
3. 检测到已有业务表且 Flyway 历史有效、数据库版本不高于源码时，每次源码更新均先暂停 Web 和 Java 进行备份，保留 MySQL、Redis 与持久卷；不只在需要新迁移时备份。
4. 备份全部数据库表的行数与校验和、上传文件（包括私有举证）、配置及挂载清单，写入受保护的 `.local/backups`。
5. 独立 MySQL 容器导入备份，检查全表校验和、数量、文件哈希、订单归属与配额；新版备份额外检查结算总额及退款数量和金额约束。
6. 启动新版，Flyway 执行尚未执行的迁移。V13—V17追加本地凭据、履约运营、持久消息、模拟账务与集合索引；不修改V1—V12。原字段保持，缺失阶段从升级时开始计时，历史金额保存为期初，不伪造旧流水。
7. 健康与冒烟检查通过后开放访问。员工旧会话在迁移时撤销，需重新登录。

新部署使用同一个 Compose 项目及持久卷。不要修改任何已经执行的迁移（以数据库 `flyway_schema_history` 为准），后续变更继续新增迁移；不能清空数据库或删除原卷代替升级。

## 独立验收

使用不同 Compose 项目名、端口和镜像标签，例如 `campuseats-improvement-20261026` 与 `28087`。迁移先在独立恢复副本演练，角色体验使用成功CI的同一应用制品。运行前检查名称和端口占用，不复用来源不明资源；验收项目产生的数据不复制回日常数据库。

验收镜像通过 `SERVER_IMAGE`、`WEB_IMAGE` 显式命名，避免覆盖其他项目使用的标签。密钥与 `.env` 留在 `.local`，不要输出或提交。

## 失败与回滚

数据库 DDL 不应假设能整体事务回滚。迁移失败时暂停应用写入，保留失败现场及升级前备份，不自动删除或重建业务数据。

启动脚本记录旧镜像、运行状态以及升级前后的数据库结构和完整Flyway历史指纹。候选启动失败时先停止候选应用；只有数据库结构及迁移历史均未变化、旧应用此前正常运行且旧镜像齐全时，才尝试恢复旧应用镜像并检查健康。自动恢复成功仍以发布失败退出，不将回退当作新版发布成功。结构发生变化、结果未知或回退失败时，保持维护状态并保留现场；记录位于 `.local/releases/`。

回退需要配套恢复升级前数据库、上传文件和原运行镜像；仅切换旧镜像不能撤销表结构变化。先在独立容器验证恢复，再在维护窗口执行恢复。升级后若已有新写入，恢复旧快照会丢失这些写入，必须先另行保存并决定恢复范围。

备份和回滚材料保存在受保护的本机 `.local`。清理重复镜像前可先用 `docker image save` 导出匹配备份的镜像，并记录 SHA-256；需要回滚时先 `docker image load`。只清理明确归属 CampusEats 的冗余容器、镜像和本轮验收专用卷，禁止全局 prune。

本机维护采用“只保留最新版”的策略：新版健康、业务数据及文件一致、镜像安全门禁和最新备份独立恢复均通过后，删除明确归属本项目且无当前引用的旧应用镜像；旧验证、旧日常恢复集、历史验收备份和旧镜像导出包按明确清单移入回收站。当前恢复集以 `.local/backups/LATEST.json` 和 `LATEST.txt` 为准；同CI应用制品、四服务镜像包和配套恢复清单的位置见[当前版本记录](verification/current.md)，这些材料须配套保留。未来升级过程中的临时留底仍用于防止发布失败丢失数据，成功后按新版本结果替换，不继续累计旧版回滚材料。此策略不授权清理其它项目、日常业务卷或归属不明的匿名卷。

源码构建可能复用旧系统包层：Dockerfile里有更新命令不代表实际执行了更新。源码开发环境应刷新过期运行层并扫描实际镜像。已采用CI制品的环境应修复CI构建并重新获取通过门禁的包，不以本机重建替代同一制品，不在运行容器中手改包或放宽门禁。

菜单缓存属于可重建数据，不包含在数据库／上传恢复集内。缓存使用epoch和代际封装；跨缓存格式回滚到旧镜像时，应在暂停Web／Java、恢复匹配数据库与上传文件后，仅清理本项目Redis中的菜单键，再启动应用。保留限流等其它Redis状态，不能用全库清空替代。以下命令只针对日常项目的派生菜单键，不能在仍接受业务写入时执行：

```powershell
docker compose -p campuseats-v1 exec -T redis sh -c 'export REDISCLI_AUTH="$REDIS_PASSWORD"; redis-cli --scan --pattern "campus:store:*:catalog" | while IFS= read -r key; do redis-cli UNLINK "$key" >/dev/null; done'
```

历史支付、退款或完成时间缺失时标记或保留为未知，不以订单／任务创建时间冒充实际发生时间；按日统计不计入没有可验证事件日期的历史金额。缺少完成时间的历史订单不能自动判定7天售后窗口。

## 构建与旧数据库注意事项

后端镜像使用 `MAVEN_MIRROR_URL` 构建参数选择 Maven 源，默认值见根目录 `Dockerfile`，可改为 `https://repo.maven.apache.org/maven2`。直接调用 `docker compose build` 前也应保留旧镜像；`start.ps1` 会先建立 `rollback-时间戳` 标签，构建失败不会停止旧应用。

无 Flyway 历史的非空数据库不能交给启动脚本自动 baseline。先保留旧镜像、数据库与上传备份，再恢复到独立克隆。可用 `scripts/migration-preflight.ps1 -ProjectName <克隆项目名>` 检查重复订单号、用户标识和孤立归属，并人工对照 `V1__legacy_schema.sql`；脚本不是完整 schema 一致性证明，也不会自动解决冲突。

只有确认克隆 schema 与 V1 一致后，才能在该克隆明确使用 `SPRING_FLYWAY_BASELINE_ON_MIGRATE=true`、`SPRING_FLYWAY_BASELINE_VERSION=1` 做一次性基线，之后移除配置，由 Flyway 执行后续迁移。克隆验收通过后再规划目标库维护窗口；不要对未知结构的日常库直接复制这些设置。
