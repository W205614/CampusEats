# 多校区版本升级与回滚

## 升级

1. 完成后端、前端、接口契约和独立容器验收；日常数据不用于写入式测试。
2. 保留当前运行容器对应的应用和 Web 镜像。运行 `scripts/start.ps1` 会先构建，构建失败不会停止旧应用。
3. 检测到数据库版本低于源码迁移版本时，启动脚本暂停 Web 和 Java，保留 MySQL、Redis 与持久卷。
4. 备份全部数据库表的行数与校验和、上传文件（包括私有举证）、配置及挂载清单，写入受保护的 `.local/backups`。
5. 独立 MySQL 容器导入备份，检查全表校验和、数量、文件哈希、订单归属与配额；新版备份额外检查结算总额及退款数量和金额约束。
6. 启动新版，Flyway 执行尚未执行的迁移。多校区升级对应 V5—V7，维护与举证索引对应 V8。历史数据归入默认校区／店铺；历史单建立单独结算单；旧退款任务迁移到新请求并保留编号，旧任务标记已迁移，禁止重复执行。
7. 健康与冒烟检查通过后开放访问。员工旧会话在迁移时撤销，需重新登录。

新部署使用同一个 Compose 项目及持久卷。不要修改任何已经执行的迁移（以数据库 `flyway_schema_history` 为准），后续变更继续新增迁移；不能清空数据库或删除原卷代替升级。

## 独立验收

使用不同 Compose 项目名、端口和镜像标签，例如 `campuseats-platform-acceptance` 与 `28083`。从升级前备份导入数据库和文件，运行源码镜像完成迁移，再执行带写入的浏览器验收。验收项目产生的数据不复制回日常数据库。

验收镜像通过 `SERVER_IMAGE`、`WEB_IMAGE` 显式命名，避免覆盖其他项目使用的标签。密钥与 `.env` 留在 `.local`，不要输出或提交。

## 失败与回滚

数据库 DDL 不应假设能整体事务回滚。迁移失败时暂停应用写入，保留失败现场及升级前备份，不自动删除或重建业务数据。

回退需要配套恢复升级前数据库、上传文件和原运行镜像；仅切换旧镜像不能撤销表结构变化。先在独立容器验证恢复，再在维护窗口执行恢复。升级后若已有新写入，恢复旧快照会丢失这些写入，必须先另行保存并决定恢复范围。

备份和回滚材料保存在受保护的本机 `.local`。清理重复镜像前可先用 `docker image save` 导出匹配备份的镜像，并记录 SHA-256；需要回滚时先 `docker image load`。只清理明确归属 CampusEats 的冗余容器、镜像和本轮验收专用卷，禁止全局 prune。

历史支付、退款或完成时间缺失时标记或保留为未知，不以订单／任务创建时间冒充实际发生时间；按日统计不计入没有可验证事件日期的历史金额。缺少完成时间的历史订单不能自动判定7天售后窗口。
