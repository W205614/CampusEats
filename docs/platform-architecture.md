# CampusEats 多校区平台架构

Java 单体、单实例，所有业务事务在一个 MySQL 数据库内完成。继续复用原有配额、Redis 缓存失效 Outbox、限流和会话撤销机制，不引入微服务、消息队列或搜索服务。

## 归属与接口

- 平台：`/api/v1/platform/**`，校区、店铺、人员、独立测试用户、平台券、异常处置、售后介入、统计、审计和模拟结算。
- 商家：`/api/v1/merchant/stores/{storeId}/**`，显式店铺范围。通过资源 ID 操作订单、售后、评价或任务时，由服务端回查店铺授权。
- 配送：`/api/v1/courier/**`，本校区抢单池与本人任务。
- 用户：`/api/v1/user/**`，公开校区和商品发现，以及本人账号、地址、分店购物车、合单、订单、券、收藏、消息及售后。
- 消息：员工使用 `/api/v1/me/messages/**`，用户使用 `/api/v1/user/messages/**`；查询与已读操作均重新检查接收账号和当前订单权限。
- 附件：`/api/v1/evidence/{id}`，鉴权读取，`Cache-Control: no-store`。举证文件在上传卷的私有子目录，公开图片路由不允许访问该目录。

`PlatformScope` 集中处理角色及归属检查。登录会话返回 `storeId`、`campusId`；实际请求重新验证账号和授权版本。人员角色、归属、启停或密码变化使旧会话失效。通知发送前验证会话，并按服务端订单所属店铺过滤。

员工管理写入还在同一事务中按固定顺序锁定管理员集合、调用者及目标员工，再检查锁后的状态、角色、归属、首次改密标记，以及原始JTI会话的有效期、撤销状态、主体和授权版本。已通过入口认证、随后等待数据库锁的旧请求，不能在调用者被停用、降权或重置密码后继续修改人员。该低频管理锁序不扩展到正常交易路径。

统一响应为 `code/message/data/requestId`。ID、金额及长整型分值通过字符串表示；普通数量为数字，净额及收支流水允许负数。用户、商家与配送员订单采用独立显式响应，核心结算、分页、统计及模拟账务也有明确记录类型；投影遇到未知字段或错误类型会失败，避免静默丢字段。`frontend/contracts/openapi.ts` 从实际 schema 生成，核心页面类型从生成结果派生；其余历史接口仍逐步迁移。

配送员仅获取履约所需信息。完成或取消后的订单不再返回电话、房间、详细地址及联系人，配送视图不包含售后退款明细；改派后原配送员不能继续读取该订单。抢单池展示订单保存的楼栋快照，楼栋后续改名不改变历史送达信息。

## 身份与请求保护

平台创建本地测试账号，凭据绑定已有用户主键，沿用 Argon2、会话撤销和授权版本；不开放注册、短信、邮箱或实名接入。首次登录及平台重置密码后必须改密，停用、改密或重置会撤销旧会话。不存在账号、密码错误和停用账号使用统一登录失败提示；密码不写入业务审计。

员工改密同时验证原密码与新旧密码不同；原样提交返回 `PASSWORD_UNCHANGED`，不会解除首次改密限制或撤销当前会话。工作台在提交前提示，服务端仍独立执行检查；成功改密后撤销旧会话并要求重新登录。

匿名登录能力接口决定前端入口：演示模式保留共享演示编号；`trial` 模式禁用共享演示登录，并拒绝与 `demo` 同时启用及占位签名密钥。独立账号可在本机试用，但不代表已经完成真实身份或公网部署验收。微信登录适配仍需配置自己的应用并独立验收。

请求保护分层生效：公开搜索默认按来源 IP 每分钟1200次，其余公开目录读取合计3000次，均可配置；登录按来源 IP 每分钟20次，并按登录账号每分钟10次。交易写入按账号每分钟30次，适用于订单、结算和领券路径，并非所有后台写接口的通用额度。Redis 保护之外保留有容量上限的本地预算和降级，不将限流数字当作吞吐能力。数据库连接、查询、事务和锁等待也有独立超时；这些资源预算不能互相替代。

## 交易

`checkout` 是创建、支付、取消和幂等恢复的聚合边界，`orders` 是独立履约的店铺子订单。每用户、每店维护独立购物车根记录和版本。

创建时串行化同一用户的提交，按店铺顺序处理购物车，校验有效地址、商品、活动和优惠券；订单、明细、库存预占、券锁定、清理所选购物车、审计和 Outbox 同事务提交。重复幂等键同内容返回原结果，换内容返回冲突；结果不明时按请求键恢复，禁止换键重新创建。

每次报价或首次提交固定一次上海业务时间，用于营业判断、活动／券有效期、报价哈希、业务日期、库存日期和过期时间。请求跨午夜不会使同一次提交的子订单与配额日期不同；跨日重用尚未提交的旧报价会要求重新确认，已提交请求仍优先按幂等键返回原结算单。

合单支付仅调用一次模拟支付，再在同一数据库事务更新全部子订单、支付记录及券。待支付取消和超时也锁定结算单，整体释放资源。任意失败不留下部分提交。

金额以整数分计算。活动价、店铺券和平台券按固定顺序叠加；门槛分别使用活动后和店铺券后的商品额。最大余数法按稳定明细顺序处理分摊尾差；规则、价格、费用、地址和分摊结果保存为快照。

## 履约与售后

订单行锁、版本和条件更新保护接单、备餐、派单、抢单、取餐与送达。配送任务可以由本校区配送员领取；已领取任务的完整地址只向获派人员提供。自取码只在用户侧展示，由商家核销；失败次数落库，平台可重置。

售后与履约状态分开。一个子订单同时只允许一个占用退款额度的活动申请；拒绝和撤销释放数量及金额。退款按原商品实付的确定性单位分摊计算，累计数量和金额不能超过原购买数量及实付。已完成订单退款不改变完成事实，不恢复已消耗配额。

每个售后审批创建独立 `refund_request`。任务领取使用行锁和 `SKIP LOCKED`，具有租约、稳定请求编号、条件完成和有限重试。模拟退款失败不提前增加已退款金额；过期租约可重领，失败任务可人工恢复。

## 服务时限与人员交接

`FulfillmentStages` 在订单业务事务中保存阶段、递增阶段序号、开始时间与截止时间。接单、备餐、待分配、待取餐、配送、自取默认时限依次为10、30、15、15、60、120分钟，各项允许1—1440分钟。店铺修改策略只影响以后开始的阶段，不重算在途阶段。历史订单缺失的阶段时间从迁移时刻开始，并标记迁移基线，不用旧下单时间伪造阶段开始时间。

平台订单的配送超时标记、阶段异常与运维检查统一使用已保存的 `order_stage.deadline_at`。旧固定60分钟扫描仅处理没有 `checkout_id` 的兼容订单；缺少配送阶段快照会单独报告。扫描修正提前置位的活动订单标记时，不递增业务版本或重复发送旧超时事件，也不重写终态订单的历史标记。

`OperationsJobs` 约每10秒选择最多200条候选记录，并按共享5秒软预算逐条处理；一条失败不会阻挡后续记录。扫描会轮转，因此10秒是调度间隔，不是每张订单的告警送达承诺。同一阶段的同类异常去重；异常记录保存发生时的阶段、截止时间和迁移标记，历史页不使用当前阶段覆盖原快照。配送员不可用异常还区分人员及授权版本，避免同一阶段再次停用时漏报。

异常工作台支持筛选和记录跟进原因。确认跟进不改变订单状态；阶段推进后解除已不成立的超时异常，配送员恢复有效、完成改派、取餐前撤回分配或订单结束后解除对应人员异常。超时不自动取消、退款或恢复库存，仍由现有合法业务操作完成处置。

配送员的“接收新任务”开关与账号启停分开，关闭接新单后仍可完成原任务。正常停用、转岗或换校区必须先移交未完成任务；紧急停用立即撤销会话并禁止新分配，由后台扫描把遗留任务列入异常队列，再由平台改派。人员修改、指派、抢单和改派采用员工行锁及订单版本复核，相关员工按稳定顺序锁定后再处理订单与任务；不能仅凭普通查询结果决定分配资格。

## 消息与事件

`PlatformScope.event` 将 Outbox、阶段更新及站内消息写入同一业务事务。消息按事件、接收类型和接收账号唯一，事务回滚不留下成功消息，重复处理不重复生成。上线前的历史 Outbox 不批量回灌为新消息。

消息仅保存摘要和资源 ID，不保存完整地址、电话或私有举证。用户与本店员工接收相关业务消息；配送员只接收履约事件白名单，发布和查询两端都排除售后退款等无关事件。人员归属及配送改派后重新检查权限，历史接收记录不会继续授予资源访问权。

站内消息支持分页、未读数、已读和离线补读。WebSocket 的本地发送成功不等于客户端已送达，Outbox 的 `SUCCEEDED` 也不是客户端阅读确认；界面仍需查询订单与消息补偿。消息与 WebSocket 均未接入短信、微信订阅或其它外部必达渠道。

工作台从消息进入订单时，非配送员先同步消息所属店铺，再跳转订单详情，使顶部店铺、履约操作和配送候选查询使用同一上下文。配送员继续使用专属履约路径；切换账号或离开页面后，迟到的已读及未读数响应不再触发旧账号导航。服务端仍独立检查当前订单及配送资格。

## 模拟流水与冻结结算

`LedgerService` 必须在现有业务事务内调用：成功支付记收入，成功退款记支出；请求中、失败或仅模拟网关凭据成功不提前记业务支出。来源唯一键保证重试防重，重复来源不能更换金额或归属。流水只追加，不提供修改和删除接口。模拟网关独立持久化的退款凭据与这里的业务流水职责不同，仍保留原租约恢复机制。

升级保存历史订单支付、退款及净额的期初快照，并记录开账时刻；不重放成功退款，不伪造历史逐笔流水及发生时间。期初余额独立展示，不计入启用首日支付额。启用首日从开账时刻起算，后续按上海自然日计算。

店铺可以查看本店流水、当日预览和历史账单；平台可以生成已结束日期的模拟结算单并运行对账。同店同日重复生成返回原单，账单冻结来源流水，退款记入实际成功日，不回写旧账单。佣金和渠道手续费为零，配送及包装费按现有订单实付纳入，负净额保留为待抵扣，不发生付款。

流水落账先取得店铺共享锁，再读取发生时间；冻结结算先取得同店排他锁，再建立查询快照。跨午夜已经入账、尚未提交的交易必须先提交，日结才选择来源；等待日结后才获得写入资格的流水按新发生日记账，避免冻结之后补进旧日流水。

`ReportQueryService` 的统计与导出都通过独立服务代理进入只读 `REPEATABLE_READ` 事务，支付汇总、退款、每日及店铺分布使用同一个数据库快照，并返回生成时间。模拟账务预览和对账也采用一致快照。对账分别展示所选发生期收支及当前全部订单余额，比较期初与后续流水；差异只报告，不自动改账。

## 查询与缓存

订单列表批量读取明细、配送、售后及退款，查询次数不随页内订单数线性增长。售后列表同样批量加载商品和举证。售后、退款和原 Outbox 通知任务沿用数组响应，支持`beforeId`游标、`state`、完整`orderNumber`、成对的`begin/end`上海创建日期；任务另支持`taskId`。上述列表以及订单、用户结算单支持可选`limit`，默认100、范围1—1000，非法值返回400。界面仍以100条加载历史，刷新按已加载条数分批读取，每批最多1000条，所有结果按ID倒序，原用户／店铺／校区授权和敏感字段过滤仍在服务端执行。

菜单缓存按进程epoch和代际判断有效性，商品提交后推进代际，持久任务异步删除派生缓存；旧回填不被新代际请求采用。保留同键合并、最多8个回源任务及1.5秒协调等待，每请求得到独立结果副本；活动和库存实时查询。

店铺和搜索分页返回 `records/nextCursor/hasMore`，默认50条、最多200条；签名游标绑定排序和筛选条件，不使用深分页OFFSET。搜索覆盖校区全部符合条件的店铺，每个商品分支先取有序候选再合并；原数组接口继续保留200店／200结果的兼容上限。字面子串匹配区分大小写，`%`和`_`不是通配符；低命中或零命中仍可能扫描较多数据。

评价与审计增加 `beforeId/limit`，默认分别100／200条，每页允许1—1000条；审计可按操作人、动作和上海日期筛选。公开评价仅来自启用校区的启用店铺，返回公开投影。V12仅新增评价和审计查询索引，不改变业务数据。全量购物车仅查询非空店并联表批量补充商品，保留空购物车版本根，避免版本归零。

员工、券模板、券钱包、活动和收藏增加 `/page` 接口，异常、消息、独立用户及模拟账务同样使用 `records/nextCursor/hasMore`，默认50条、最多200条；游标签名绑定账号、角色和筛选范围，权限逐请求重新检查。普通列表按ID倒序，收藏按店铺、类型、目标ID升序。旧集合数组接口保留形状、最多200条；完整记录应使用分页。前端列表独立管理游标，切换账号或筛选清空范围、忽略旧响应，加载失败保留同范围内已取得的数据。

钱包分页与兼容数组接口按单次请求的上海时间投影状态：未使用券到达截止时间后显示 `EXPIRED`，全部、可用及已过期筛选使用相同规则。投影不修改持久状态，锁定和已使用券维持原业务状态，实际结算仍独立校验券有效期。

## 模块与数据库边界

HTTP入口按目录发现、购物车结算、履约配送、售后退款及管理拆分，新增身份、运营和账务控制器仍只调用服务，不直接查询数据库。`platform` 组织多校区应用流程，`business` 复用配额、地址、商品、缓存与模拟网关，`finance` 记录期初、流水和冻结结算。库存和金额算法沿用现有权威实现，兼容入口不复制新规则。

模块检查约束控制器不持有数据库访问对象，并检查选定核心服务不依赖 HTTP 视图；它不等于完成了所有包的循环依赖验证。现阶段仍在一个后端、一个数据库里维持事务，未引入分布式事务或消息中间件。

V13—V17分别补充本地账号、履约运营、持久消息、模拟账务与集合索引，V18—V19只增加对账流水与订单覆盖索引，历史迁移保持原文件。升级比较历史表的原列及原主键记录，新增列、表和期初记录单列核对；迁移失败停止，不自动修复历史或基线化。新功能不自动删除原订单、退款、审计和业务图片。

## 边界

本文描述当前源码机制；对账按订单聚合流水并通过CTE复用余额结果，V18—V19索引覆盖两侧读取字段，单条SQL以 `SET_VAR` 将每张内部临时表上限设为32 MiB，执行后恢复连接原值。源码、运行制品、角色验收及恢复材料状态分别以[当前版本验证与维护记录](verification/current.md)列明的证据为准。单机、单实例和模拟资金定位保持不变。

真实微信支付、商户资金划转、渠道对账和真机验收未接入。模拟流水及结算不证明真实支付回调、结果未知补偿、第三方网络语义或会计合规。共享演示身份仍仅供假资料使用，独立本地账号也不构成实名体系。

单实例停止期间没有第二个后端接替；缓存代际、WebSocket连接、上传空间账本和部分降级预算具有进程范围，不能直接通过增加后端副本获得正确扩容。工具交付不表示已经注册系统任务、接通异机备份或外部告警；未宣称生产峰值容量、多实例正确性或长期可用性。
