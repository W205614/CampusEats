## 午餐场景容量

使用原有午餐脚本与固定阈值：30 个用户、3 个店员、300 秒、0/90/180 秒三轮交易、90 次完整交易；205 家店、1,025 个商品和 200,000 条合成历史订单，80% 历史集中在热店。观察者查询 90 天账务，未缩小日期范围。

首轮失败报告保留在 `performance/report.json`：9,654 次 HTTP 请求全部成功，90 次交易完成，交易 P95 为 7,799.38 ms，但热店对账 P95 为 1,730.38 ms，超过读取 1,000 ms 目标，整体未通过。MySQL 当时配额为 768 MiB。后续同一数据集的只读探针区间记录到内存上限触发、直接内存回收和交换页增长，未出现 OOM；候选 SQL 改写没有稳定收益，未合入。

第二轮停止本任务其他验收容器，将隔离 MySQL 调整为 1 GiB（memory+swap 上限 2 GiB），仍保留原代码、数据和阈值。9,686 次请求全部成功，90 次交易完成、交易 P95 为 4,126.23 ms，但对账 P95 为 1,480.39 ms，因此仍为失败。计时区间未增加内存上限事件，SQL 仍为主要开销。报告为 `performance-1g/report.json`，没有覆盖首轮结果。
