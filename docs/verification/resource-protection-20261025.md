# 2026-10-25 资源保护复查与交付

本轮沿用个人维护、单机单实例、共享演示身份与模拟支付退款的边界。所有写入式验收使用独立项目 `campuseats-improvement-20261025-protection`、本机端口28087、独立凭据和MySQL／Redis／上传卷；日常数据没有接收验收夹具。

## 五项修复

1. 私有举证每次鉴权后检查文件，再同步流式返回PNG，固定16KiB缓冲，不再把整图读入Java堆。默认全局4、每账号2个读取连接，每账号120次／分钟，账号状态最多10000项；缺文件、断线及异常释放名额，保留 `no-store`。工作台区分429／503与权限拒绝，只允许手动重试。
2. 限流每请求先通过有界本地窗口，再访问Redis。缓存淘汰导致Redis计数丢失时，本进程的预算仍有效；降级不重复计数。本地状态不跨进程持久化，进程和Redis状态同时丢失后的限流不属于此保证。
3. 每店最多500个菜品和套餐（含停售项）、每菜品20组口味、套餐50项组成。新增时锁同一店铺行后联合计数，跨类型并发不能突破最后名额。已有商品可编辑，历史超限整店读取明确拒绝，不删除或截断数据。日常发布前目录核对最大为4项，没有超限店铺。
4. 限流与菜单Redis命令共用最多4个在途名额；失败后短路5秒，仅一个恢复探测。菜单缓存使用进程epoch与256条带代际，事务提交后只推进代际，持久通知稍后删除Redis键；旧回填和旧进程缓存不会被新代请求采用，商家响应不再等待慢读锁或Redis删除。首次故障仍可能承担Redis超时，1.5秒协调等待不是整个请求的耗时上限。
5. 搜索各分支有序截取每页数量加1条，再合并，候选最多402条。进一步按实测瓶颈新增V11的两项 `(store_id,status,id)` 索引，以商品表驱动按序早停；保留字面、大小写、分类、营业及游标语义，兼容数组接口仍有200条上限。V1—V10未修改。稀疏或零命中仍可能扫描索引，不能宣称所有搜索成本恒定。

首个功能提交为 `5250efaa073c473f279f69ddb6e330701be9624b`；根据并发验收定位排序瓶颈后的最终功能提交为 `530fb8ba32a6936aa3c5ddf42f529cd0e142062f`。

## 扩展目录与故障证据

夹具为100家店、每店250菜品及250套餐，共50000个商品，另有25000条口味和25000项套餐组成。检查三个500商品菜单、完整50k分页、稀疏标记、大小写、字面 `%_`、伪通配符匹配、零命中及尾页，全部与独立SQL顺序结果一致。修复探测驱动的空字符串SQL后复用同一夹具，不重复生成数据；原失败报告保留。

最初仅约束分支候选的260次HTTP读取P95为177.41ms。30客户端、60秒、每客户端约1秒间隔交替读取500商品菜单与50条搜索页时，1696次请求无错误，但P95为1288.38ms，未达1秒目标，故暂停发布。

执行计划证明两个分支仍分别排序约25000行，MySQL资源样本CPU峰值528.36%（Docker多核口径）。隔离索引实验的10种输入组合分别进行原方案和有序方案各3次执行计划比较，typed候选完全相同；广泛匹配、每支51条时，原方案两个分支各扫描约25000行，有序方案约61／52行，分支排序节点消失。稀疏／零命中仍扫描较多行，部分零命中观察耗时高于原形态，未隐去该权衡。实验索引在finally移除后才交由Flyway V11正式创建。

最终功能镜像上的同一夹具完整分页再次通过：260次HTTP读取，P95为54.16ms。原始执行计划毫秒是固定数据和同机资源条件下的观察值，不能把SQL节点耗时换算为应用TPS。

Redis真实暂停复验通过：首请求200，耗时1066.03ms；短路后的3秒内30客户端完成600次读取，P95为114.28ms，零429及非预期错误，恢复探测闭合。Docker健康状态恢复另耗时约6.09秒，四服务无OOM或异常重启。第一次驱动过早检查恢复后的Docker健康状态失败，业务阶段当时已通过；该失败报告保留，修正为有上限等待后完整复验通过。

真实限流键丢失验收：1200次搜索成功，第1201次429；仅删除已扫描确认的一个隔离Redis搜索计数键后，再请求两次仍429且键未重建，均带 `Retry-After: 60`。这是预期429的边界测试，不计入正常负载通过率；未调整应用限额或清空Redis。
